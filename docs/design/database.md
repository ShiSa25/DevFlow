# Database design

PostgreSQL, through the existing Drizzle schema in `src/db/schema.ts` and the existing `drizzle/` migration directory. `npm run db:generate` writes SQL. `npm run db:migrate` applies it. Process startup does not migrate, and importing `src/db` does not connect.

This pull request does not add tables. The Drizzle journal stays empty until the milestone that implements each table.

The Better Auth Drizzle adapter addresses tables by the schema property names `user`, `session`, `account`, and `verification`, and it addresses columns by the camelCase property names in [its field mapping](https://www.better-auth.com/docs/adapters/drizzle). SQL identifiers below are snake_case. The Drizzle property keeps the library's camelCase name (`accountId: text("account_id")`). Pass that schema object into `drizzleAdapter`. Leave `usePlural` off. Do not point the adapter at a second schema file.

Auth primary keys are text, generated by Better Auth. Project and task primary keys are UUIDs generated in PostgreSQL (`gen_random_uuid()`). `project.owner_id` stores `user.id`, the DevFlow user id, not the GitHub id.

## Auth tables

These four tables are what Better Auth 1.7.12 uses for GitHub sign-in and database sessions. Unused nullable columns stay, because the adapter expects them. The implementation has to satisfy that version's schema check.

### `user`

| Column | Constraint | Role |
| --- | --- | --- |
| `id` | text primary key | DevFlow user id |
| `name` | text not null | Display name from GitHub |
| `email` | text not null, unique | Synthetic `{githubUserId}@users.noreply.devflow.invalid` |
| `email_verified` | boolean not null, default false | Always false for the synthetic address |
| `image` | text null | GitHub avatar URL |
| `created_at`, `updated_at` | `timestamptz` not null | Library timestamps, UTC |

`user` is a quoted identifier. Email is required by the library. It is not the login key. See [authentication](authentication.md).

### `session`

| Column | Constraint | Role |
| --- | --- | --- |
| `id` | text primary key | |
| `user_id` | text not null, references `user(id)` on delete cascade, indexed | |
| `token` | text not null, unique | Raw session token. The cookie holds a signed form of this value. |
| `expires_at` | `timestamptz` not null | Expiry. Default lifetime 7 days, sliding after 1 day. |
| `ip_address`, `user_agent` | text null | Library metadata from the sign-in request. Not used for authorization. |
| `created_at`, `updated_at` | `timestamptz` not null | |

### `account`

| Column | Constraint | Role |
| --- | --- | --- |
| `id` | text primary key | |
| `user_id` | text not null, references `user(id)` on delete cascade, indexed | |
| `provider_id` | text not null | `github` |
| `account_id` | text not null | Decimal GitHub user id |
| `access_token`, `refresh_token`, `id_token` | text null | Present for the adapter. Application hooks write null. |
| `access_token_expires_at`, `refresh_token_expires_at` | `timestamptz` null | Written null |
| `scope` | text null | `read:user` when the library stores it |
| `password` | text null | Unused. Email-and-password is off. |
| `created_at`, `updated_at` | `timestamptz` not null | |

Unique `(provider_id, account_id)`. That pair is the provider identity. The 1.7.12 lookup throws if more than one row matches it, so the database rejects the duplicate. The core field list in that version does not declare this composite unique itself; this schema adds it.

### `verification`

OAuth `state` is stored here because a database adapter is configured. Rows are short-lived (10 minutes in this version) and deleted when the callback finishes. The table is not an email-verification feature and not a product table.

| Column | Constraint |
| --- | --- |
| `id` | text primary key |
| `identifier` | text not null, indexed |
| `value` | text not null |
| `expires_at` | `timestamptz` not null |
| `created_at`, `updated_at` | `timestamptz` not null |

No rate-limit table. The library's production rate limit can use its default in-memory store. That store is per process and is not part of authorization.

## `project`

| Column | Constraint |
| --- | --- |
| `id` | uuid primary key, default `gen_random_uuid()` |
| `owner_id` | text not null, references `user(id)` on delete cascade |
| `name` | text not null, check length 1–100 after the application has trimmed it |
| `description` | text null, check null or length at most 5,000 |
| `archived_at` | `timestamptz` null. Null means active. |
| `created_at`, `updated_at` | `timestamptz` not null |

Names are not unique. New rows are active (`archived_at` null).

While `archived_at` is set, the server still returns the project and its tasks to the owner. The only writes the server allows in that state are clearing `archived_at` (restore) and deleting the project row. Deleting the project cascades to its tasks. Editing the project name or description, and creating, updating, or deleting an individual task, are refused by the server operation and leave both tables unchanged. A missing or other-owner row is the same not-found result as any other hidden record. The database does not encode that distinction with a second constraint. The operation rules are in [server operations](server-operations.md).

`updated_at` changes when the project is created, when its name or description changes, and when it is archived or restored. No trigger and no task statement updates it. Task creates, edits, and deletes leave `project.updated_at` as it was.

Index `project_owner_list_idx` on `(owner_id, updated_at desc, id desc)` supports the owner-scoped list and the five most recently updated active projects. Active versus archived is a predicate on `archived_at` in that same query (`is null` or `is not null`). One list, two filters. The tie-breaker is `id` descending.

Deleting a user is not a pilot feature. The cascade is there so an `owner_id` cannot point at a missing user if a row is removed later.

## `task`

| Column | Constraint |
| --- | --- |
| `id` | uuid primary key, default `gen_random_uuid()` |
| `project_id` | uuid not null, references `project(id)` on delete cascade |
| `title` | text not null, check length 1–200 |
| `description` | text null, check null or length at most 5,000 |
| `status` | text not null, default `todo`, check in `backlog`, `todo`, `in_progress`, `done` |
| `priority` | text not null, default `medium`, check in `low`, `medium`, `high`, `critical` |
| `due_on` | `date` null. A calendar date, not a timestamp. |
| `created_at`, `updated_at` | `timestamptz` not null |

The status and priority checks store stable ids. The UI labels are Backlog, Todo, In Progress, Done, and Low, Medium, High, Critical.

Indexes for the queries this pilot actually runs:

- `task_project_created_idx` on `(project_id, created_at desc, id desc)` for the default list.
- `task_project_due_idx` on `(project_id, due_on, id)` for nearest-due-date sorting.

Priority order is `critical`, `high`, `medium`, `low`, expressed as an `ORDER BY` case, not as alphabetical order on the text. That sort does not get its own index. There is no all-project task inbox, so there is no cross-project task index.

`ON DELETE CASCADE` from `project` to `task` is the permanent-delete rule. One `DELETE` of the owned project removes its tasks in the same statement. The application does not issue a separate task delete first.

## Dates

`timestamptz` columns store absolute instants. The application writes JavaScript `Date` values, which the adapter already uses for its own timestamp fields. Due dates use PostgreSQL `date`.

Overdue means `due_on` is earlier than today's calendar date in `APP_TIME_ZONE`. A null due date is never overdue. A due date equal to that calendar date is not overdue. Archived projects and their tasks are absent from every dashboard aggregate.

## What is not stored

No invitations, roles, labels, comments, attachments, or GitHub repository ids. No second copy of the GitHub user id on `user`. The account row is the identity. The GitHub access token is not retained; the nullable token columns exist for the adapter and stay null.
